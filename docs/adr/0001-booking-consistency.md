# ADR-001: Согласованность бронирований между сервисами

Статус: принято. Дата: 24.10.2026.

## Контекст

По ТЗ Booking Service создаёт бронирования, а Hotel Service управляет доступностью номеров. У каждого сервиса своя H2. Нужно исключить пересекающиеся брони и корректно обрабатывать ошибки, тайм-ауты и повторную доставку запросов. Для учебного проекта достаточно синхронного REST-взаимодействия и локальных транзакций.

## Решение

Используем двухшаговое подтверждение с компенсацией:

1. Booking сохраняет бронь в состоянии `PENDING` и завершает локальную транзакцию.
2. Booking вызывает внутренний `confirm-availability` в Hotel. Hotel блокирует строку номера, проверяет операционную доступность и пересечение дат, сохраняет слот в `room_reservations` и увеличивает `times_booked` в одной транзакции.
3. При успехе Booking переводит бронь в `CONFIRMED` отдельной локальной транзакцией.
4. При ошибке Booking переводит бронь в `CANCELLED` и, если номер уже выбран, вызывает `release`. Hotel освобождает слот и уменьшает счётчик только при первом освобождении.

Слоты в Hotel — локальная копия дат для атомарной проверки доступности. Сервисы не обращаются к чужой БД. Поле `available` отражает ремонт или вывод номера из эксплуатации; занятость определяется по активным слотам и датам.

HTTP-вызовы выполняются вне транзакций БД. По умолчанию тайм-аут подключения — 1 секунда, чтения — 2 секунды. При сетевых ошибках, ответах `5xx` и отсутствии экземпляра Hotel в Eureka выполняются до трёх попыток с паузами 100 и 200 мс. При автоподборе конфликт `409` позволяет перейти к следующему рекомендованному номеру; после неоднозначного результата, например тайм-аута, выполняется отмена с компенсацией.

Повторное создание определяется по паре `(userId, requestId)` и параметрам запроса. Hotel использует `bookingId` для идемпотентности подтверждения и освобождения. Освобождённые записи сохраняются: запоздалый `confirm` не должен восстановить отменённую бронь. Ключевые события логируются с `bookingId`.

## Рассмотренные альтернативы

- Общая БД: упростила бы транзакции, но связала бы сервисы и противоречила требованию раздельных хранилищ.
- Глобальная распределённая транзакция: потребовала бы дополнительной инфраструктуры и не соответствует требованию локальных транзакций.
- Асинхронная сага через брокер: возможна, но для текущих сценариев добавляет лишние компоненты и обработчики.

## Последствия

- Каждый сервис самостоятельно фиксирует изменения, повторные запросы не создают дубликаты слотов и не меняют счётчик повторно.
- Между шагами состояние временно несогласованно; тайм-аут не доказывает, что Hotel не успел сохранить слот, поэтому требуется `release`.
- Если освобождение не удалось после повторов, сохраняется `compensationRequired=true`. Повторный `DELETE /api/bookings/{id}` запускает компенсацию ещё раз.
- Автоматическое восстановление после остановки процесса не реализовано. H2 хранит данные только до перезапуска; проект рассчитан на учебный запуск.
